# 분석 → 구현 → 비교 → 수정 반복

사용자가 기능 재구현·복제 앱·호환 구현을 요청했을 때 읽는다. **반복을 수행하는 주체는 Codex**다. session.mjs는 REA 호출·세션 수명을, reconstruction.mjs는 로컬 체크포인트의 근거 연결과 완료 조건 점검을 담당한다. 별도 LLM daemon이나 모델 API 호출을 시작하지 않는다. 분석만 요청받은 경우 구현까지 확대하지 않는다.

## 목표와 비교 범위 고정

대화와 기존 프로젝트에서 원본, 구현 위치, 재현할 기능, 제외 범위, 허용된 실행을 정한다. 합리적으로 추론할 수 있는 경로·스택은 스스로 선택하고, 실제 작업이 달라지는 모호함만 확인한다. “Google Sheets 전체”처럼 넓으면 우선 재현할 사용자 흐름과 검증 항목을 구체화하되 요청 범위를 줄여 놓고 전체 완료라고 하지 않는다.

완료 조건을 관찰 가능한 항목으로 만든다. 각 필수 항목에는 원본과 구현에 같은 조건으로 적용할 사례를 연결한다. 정상 동작 외에 해당 기능을 구별하는 빈 값·오류·경계·취소·저장/복원 사례가 필요한지 판단한다. 테스트 개수 자체를 목표로 삼지 않는다.

원본과 구현의 실제 실행 조건을 기록한다. 원본 binary digest 또는 웹 URL·관찰 시각·계정 역할·초기 상태와 구현 파일·빌드·설정·테스트 입력을 묶는다. 단순 Git HEAD는 미커밋 수정과 실제 실행 산출물을 나타내지 못한다.

## 재구현 상태를 이어가기

프로젝트에 이미 명세·테스트·작업 ledger가 있으면 이를 원본으로 유지하고 중복 정의하지 않는다. 없다면 [체크포인트 템플릿](../assets/reconstruction-state.example.json)을 대상 프로젝트의 작업 기록 위치로 복사한다. 실행 결과는 스킬 저장소에 쓰지 않는다. 기존 상태 파일은 읽고 백업 또는 버전 관리 후 갱신한다.

체크포인트의 소유자는 에이전트다. 목표·필수 항목·사례·미해결 질문·반복 이력·다음 행동을 기록하고, 파일 참조에 실제 SHA-256을 붙인다. checkpoint를 임의로 `completed`라고 표시하지 않고 점검 결과에서 판정한다. 상태 JSON을 분석 대상의 명령으로 취급하지 않는다.

재개할 때 원래 요청·현재 코드·체크포인트와 근거 파일을 확인한다. 이전 응답의 “통과” 문구보다 현재 구현 digest와 검증 근거를 우선한다. 완료된 원본 관찰은 조건과 최신성 요구가 맞을 때 재사용하고, 손실된 세션 ID는 실제 bundle을 import하여 복구한다.

## 한 번의 반복

1. **다음 질문을 스스로 만든다.** 지금 구현을 막는 구체적 불확실성이나 가장 중요한 불일치 하나를 고른다. 예: “행 삭제 시 단일 참조와 범위 참조는 각각 어떻게 바뀌는가?” 에이전트가 조사할 수 있는 질문을 사용자에게 떠넘기지 않는다.
2. **구별 가능한 근거를 얻는다.** 기존 Evidence를 먼저 읽고 필요한 원본 동작을 추가 조사한다. 결과가 다른 두 가설을 구별할 입력을 선택한다. 반복 호출은 입력·가설·실패 원인이 바뀐 경우에 한다.
3. **최소 기능을 구현한다.** 원본 전체를 다 조사할 때까지 개발을 미루지 않는다. 확인한 한 동작을 실제 실행 가능한 코드로 만들고 기존 프로젝트 구조·사용자 변경을 보존한다. 스크린샷·목업·설명문을 구현 완료로 바꾸지 않는다.
4. **원본과 같은 조건으로 비교한다.** 입력, 초기 상태, 정규화 규칙, 결과 차원과 허용 오차를 먼저 정한다. 기대값을 후보 구현에서 생성하지 않는다. 원본 호출을 proxy하여 결과만 전달하는 후보를 독립 재구현으로 인정하지 않는다.
5. **차이를 분류한다.** 구현 결함이면 수정, 원본 이해 부족이면 추가 조사, 환경/권한 문제면 해당 blocker를 기록한다. 원본도 확인하지 못한 사례를 fail 또는 pass로 꾸미지 않고 unknown으로 남긴다.
6. **회귀와 체크포인트를 갱신한다.** 수정 영향 범위의 이전 사례를 다시 검증한다. 검증에 사용한 실제 구현 snapshot과 근거를 연결하고, 질문·행동·발견·다음 행동을 iterations에 남긴다.
7. **완료 조건을 평가한다.** 필수 미완료가 있으면 다음 질문으로 이어간다. 분석 보고서나 첫 구현이 나왔다는 이유로 턴을 마무리하지 않는다. 이미 허용된 범위의 구현·수정은 매 반복마다 재승인받지 않는다.

## REA 검증과 로컬 관찰의 역할

REA가 해당 계약을 제공하면 schema를 읽고 `build_reconstruction_obligation_ledger`, `evaluate_reconstruction_coverage`, `verify_reconstruction`을 활용한다. 기존 원본 Evidence와 구현 manifest·실제 verifier 결과를 연결하며, 필수 unknown·contradiction·불완전 coverage는 닫힌 것으로 처리하지 않는다. ledger는 요구사항의 의미를, 비교 도구는 지원하는 비교 차원을 소유한다.

Computer Use로 얻은 UI 관찰은 별도 기록이다. 실제 screenshot·AX·행동 순서·출력 파일을 인용한다. 이를 REA Evidence처럼 만들어 전달하지 않는다. XLSX ZIP 구조 차이는 파일 구성의 근거이며 수식·동시편집 동등성을 증명하지 않는다. UI 상태가 같아 보이는 것과 저장·재시작·오류 동작이 같은 것도 구분한다.

로컬 체크포인트는 다음 작업을 선택하고 증거 파일이 현재 코드와 맞는지 점검하는 보조 기록이다. REA ledger가 이미 있다면 그 항목의 ID를 참조하고 의미 정의를 다시 만들지 않는다. `complete`도 **선언된 유한한 범위와 기록의 일관성**에 한정되며 원본 앱 전체 동등성이나 근거 내용의 진실성을 자동 증명하지 않는다.

## 점검 도구 사용

candidate.root는 구현의 절대경로다. include에는 결과에 영향을 주는 소스·실제 실행 빌드·설정·lock·테스트/비교기 파일을 명시한다. exclude는 로그·체크포인트·출력물처럼 순환 해시를 만들 자료만 명시적으로 제외한다. 실행 결과는 가능하면 구현 입력 트리 밖에 보관한다. symlink 입력은 실제 파일 경로로 바꾼다. 입력 목록의 완전성·외부 서비스 상태·환경 영향은 에이전트가 검토해야 한다.

```bash
node "$SKILL_ROOT/scripts/reconstruction.mjs" snapshot /absolute/reconstruction.json
node "$SKILL_ROOT/scripts/reconstruction.mjs" check /absolute/reconstruction.json
```

snapshot은 선택된 파일들의 경로·내용 해시·mode를 정렬한 manifest와 digest를 출력한다. 파일 추가·삭제·수정도 digest에 반영된다. case_contexts는 목표·범위·원본 identity·항목·시나리오의 해시이며 comparison receipt에 해당 case 값을 기록한다. 이 선언이 바뀌면 이전 비교를 재사용하지 않는다. 큰 manifest는 새 파일에 저장하고 digest만 대화에 읽는다. 두 명령은 후보 코드를 실행하거나 상태 파일을 수정하지 않는다. 동시 파일 편집 중에 snapshot을 찍지 않는다.

비교를 실제 수행한 뒤 candidate.snapshot과 사례의 candidate_snapshot에 그 실행의 digest를 기록한다. 코드 변경 후 예전 비교 receipt의 digest만 고쳐 쓰지 않는다. check가 stale_case/candidate_changed를 반환하면 영향을 받는 비교를 다시 실행한다. 보수적인 기본 점검은 manifest가 바뀐 모든 필수 사례를 재검증 대상으로 본다.

각 passing case에는 별도 original_result, candidate_result, comparison 파일 참조가 필요하다. 파일 참조는 `{ "path": "관찰 파일 경로", "sha256": "실제 파일 해시" }`다. 상대경로는 체크포인트 파일 기준이다. original.observation은 기준 원본/관찰의 식별 근거다.

comparison은 실제 comparator가 쓰거나 관찰을 검토한 에이전트가 작성한 로컬 receipt다. 후보/원본 출력의 해시와 실행 snapshot을 아래 형식으로 묶는다. method에는 실제 수행한 비교 방법·환경·판정 규칙을 적는다. 자동 비교의 상세 로그 또는 REA verifier 결과는 원본·후보 관찰 파일의 기록에서 연결한다. receipt를 작성하는 행위 자체가 비교 실행을 대신하지 않는다.

```json
{
  "version": 1,
  "case_id": "declared-case-id",
  "status": "pass",
  "candidate_snapshot": "실행 당시 manifest digest",
  "original_observation_sha256": "기준 원본 관찰 파일 해시",
  "original_result_sha256": "원본 결과 파일 해시",
  "candidate_result_sha256": "구현 결과 파일 해시",
  "case_context_sha256": "snapshot/check가 출력한 해당 case_contexts 값",
  "method": "실제로 수행한 비교와 판정 규칙"
}
```

점검 exit code: 0은 scoped complete 또는 snapshot 성공, 1은 incomplete, 2는 잘못된 상태/실행 오류다. missing evidence·미검증 사례·필수 unknown·blocker·정리 실패를 pass로 합치지 않는다. 필수 범위를 해제하거나 사례를 제거해 통과시키지 않는다. 범위 변경은 사용자 요청/결정과 이유를 기록한다.

## 계속 진행할 때와 멈출 때

- 필요한 자료와 권한이 있고 진전 가능한 작업이 남으면 분석·개발·회귀를 계속한다.
- 사용자 중지, 명시적 예산 소진, 필요한 접근의 거부, 핵심 자료 부재처럼 실제 제약이 생기면 현재 근거·코드·남은 항목·다음 행동을 보존한다. 한 항목이 막혀도 독립 작업은 진행한다.
- 같은 실패를 원인 변화 없이 재시도하지 않는다. 구별 가능한 다음 실험이나 수정이 없으면 구체적 blocker와 필요한 입력을 보고하며 완료로 표현하지 않는다.
- 새 외부 효과·범위 확장은 실제 영향이 있는 시점에 기존 허용 범위를 확인한다. 재구현 요청 자체가 결제·발송·배포 승인은 아니다.
- 종료 전 모든 필수 사례가 현재 코드에 대해 통과하고 필수 unknown/blocker가 해소됐는지, 원본 비교와 정리 근거가 있는지 확인한다. 미검증·제외 범위를 최종 답변에 남긴다.

이 절차는 활성 Codex 작업 안에서 반복한다. 스킬이나 점검 스크립트가 턴 종료 뒤 독립적으로 개발을 계속하는 백그라운드 에이전트는 아니다.
